# WASM 配信時の転送量（YTA-12）

`main.wasm` を本番で配信するときに転送量をどう減らすかの判断と、その手順を残す。
YTA-10 の実機検証で iPhone が受け取った 21.4 MB は、開発サーバ（`cmd/serve`）が
圧縮していないことによるもので、ビルドサイズそのものは変わっていない。

対象バージョン: Go 1.25.4 / Ebitengine v2.10.2

## 結論

**配信時の事前圧縮で対応する。** `make dist` が非圧縮・gzip・brotli の 3 つを生成するので、
配信側は `Content-Encoding` を付けて圧縮済みのファイルを返す。

brotli で **21.4 MiB → 3.80 MiB（-82%）**。これは `text/v2` を使う限り避けられないコード増分を
含んだままの値で、フォントのサブセット化より効果がはるかに大きい。

フォントのサブセット化は**見送る**。理由と再検討の条件は「採用しなかった手段」を参照。

## 実測値

`make dist` と同じ手順（出力先 `dist/main.wasm`）で測った値。ブランチ `vividnasubi/yta-12-reduce-wasm-transfer-size`、
コミット `fee6f57` 時点。

| ビルド | 非圧縮 | gzip -9 | brotli -q11 |
| --- | --- | --- | --- |
| **通常（採用）** | **22,436,383**（21.4 MiB） | **5,542,382**（5.29 MiB） | **3,990,332**（3.80 MiB） |
| `-ldflags="-s -w"` | 21,896,802 | 5,439,882 | 3,926,739 |

圧縮にかかった時間（Apple Silicon・22 MB に対して）:

| 圧縮 | 時間 | サイズ |
| --- | --- | --- |
| gzip -9 | 1.6 秒 | 5,542,382 |
| brotli -q5 | 0.3 秒 | 4,806,023 |
| brotli -q11 | 35 秒 | 3,990,332 |

事前圧縮なので brotli の圧縮時間は配信時のコストにならない。**常に -q11 を使う。**
q5 と q11 の差は 0.8 MB あり、ビルド時に 35 秒払う価値がある。

ビルドのたびに数十〜数百 bytes の差が出る（出力パスなどがバイナリへ入るため）。
上表の下 3 桁は参考値として扱うこと。

## 生成手順

```sh
make dist
```

`dist/` に配信物一式が出る。

```text
dist/index.html      bootstrap ページ
dist/iframe.html     iframe 埋め込み確認用ページ
dist/wasm_exec.js    Go WASM runtime（GOROOT からコピー）
dist/main.wasm       非圧縮。Content-Encoding に対応しない経路のフォールバック用
dist/main.wasm.gz    gzip -9
dist/main.wasm.br    brotli -q11
```

- brotli コマンドが必要（macOS は `brew install brotli`）。無い場合は警告を出して `.br` をスキップする
- `dist/` は `.gitignore` 済み。生成物は commit しない
- HTML と `wasm_exec.js` は事前圧縮していない。合計 24 KB 程度で、テキストなら配信側の
  自動圧縮が確実に効く範囲のため

## 配信側に必要な設定

圧縮済みファイルを返すときのレスポンスヘッダ。

| ヘッダ | 値 | 理由 |
| --- | --- | --- |
| `Content-Type` | `application/wasm` | これが違うと `WebAssembly.instantiateStreaming` が失敗する。圧縮済みファイルを返すときも中身は wasm なのでこの値を保つ |
| `Content-Encoding` | `br` または `gzip` | 付け忘れると圧縮データがそのまま wasm として解釈され、起動に失敗する |
| `Vary` | `Accept-Encoding` | 圧縮版と非圧縮版を同じ URL で出し分けるため。キャッシュの取り違えを防ぐ |

配信基盤を決めるときに確認すること。

- **CDN の自動圧縮はサイズ上限に引っかかる可能性が高い。** 例えば CloudFront が自動圧縮するのは
  1,000〜10,000,000 bytes のオブジェクトで、21.4 MB の `main.wasm` は対象外になる。
  事前圧縮したファイルを置くほうが確実。上限の値は採用する基盤のドキュメントで再確認する
- **brotli は HTTPS でのみネゴシエートされる。** ブラウザは平文 HTTP では `Accept-Encoding` に `br` を
  入れないため、HTTP 配信では gzip までしか落ちない。本番は HTTPS 前提
- **別オリジンから配信する場合は `Timing-Allow-Origin` が要る。** これが無いと
  `index.html` が画面右下へ出している転送量が 0 になり、実機で圧縮後のサイズを読めなくなる
- **キャッシュ設定は未決。** 現在はファイル名が `main.wasm` 固定なので、長期キャッシュを効かせるなら
  ファイル名にビルド識別子を入れる必要がある。配信基盤の選定と合わせて決める

`index.html` が表示する転送量は Resource Timing の `encodedBodySize`（圧縮後のボディサイズ）なので、
圧縮を有効にすれば実機の表示もそのまま圧縮後の値になる。

## 採用しなかった手段

### `-ldflags="-s -w"`

圧縮後で 63,593 bytes（-1.6%）しか減らない。その代わり panic 時のシンボルが落ちるため、
実機で問題が起きたときの手がかりが減る。**割に合わないので使わない。**

### フォントのサブセット化

見送る。理由は 3 つ。

1. 使う Emoji が確定していない。現在の 12 グリフは PoC 用で、キャラクター定義が固まると変わる
2. `fonttools`（Python）をビルド依存に追加することになる。現在のビルドは Go ツールチェーンだけで完結している
3. 転送量の内訳ではコード側が支配的。同梱フォントは非圧縮で 1.47 MB（`main.wasm` 全体の約 7%）、
   gzip 換算での増分は約 0.7 MB だった。サブセット化しても圧縮後 3.8 MB から減らせるのは
   その一部にとどまり、`text/v2` が引き込むコード +6.2 MB のほうが大きい
   （内訳は [emoji-rendering.md](emoji-rendering.md)）

**再検討する条件**: 使用する Emoji が確定し、かつ圧縮後 3.8 MB では初回ロードが要求を満たさないと
判明したとき。その時点では 1 から 2 の理由が解消しているか、払う価値があると判断できる。

### `cmd/serve` の圧縮

`cmd/serve` は動作確認用なので圧縮しない（Issue の指示どおり）。
ローカルでは転送が一瞬で終わるため、圧縮しても得るものが無い。
圧縮を有効にした状態の挙動は、配信基盤を決めたあとに実配信で確認する。

## 未検証

- **実機で圧縮後の転送量を確認していない。** 上の値はローカルで圧縮したファイルのサイズであり、
  ブラウザが実際に受け取った量ではない。HTTPS の配信先が決まった時点で、iPhone Safari で
  画面右下の転送量が 3.8 MB 前後になることを確認する
- **モバイル回線での初回ロード時間も未計測。** ロード中の体験は YTA-13 で扱う
