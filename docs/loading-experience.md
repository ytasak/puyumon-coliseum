# 初回ロード中の体験（YTA-13）

`main.wasm` のダウンロードが終わるまで何を見せるか、失敗したときに何を出すかの判断と、
ロード時間の実測を残す。転送量そのものの削減は [wasm-delivery.md](wasm-delivery.md) を参照。

## 結論

ロード中は**テキストだけ**を出す。

```text
読み込み中... 2.4MB
（10 秒を超えたら）回線によっては時間がかかります。そのままお待ちください。
```

失敗したときは理由と再読み込みボタンを出す。

```text
起動できませんでした
Error: main.wasm: HTTP 404
[ 再読み込み ]
```

アートワークやキャラクターは出さない。理由は 2 つ。

1. ローディング画面のアートワーク確定は Issue の Out of scope
2. ロード中の表示は WASM の外側（HTML）なので、Emoji を出すと **OS のフォントで描かれる**。
   起動後は同梱の Twemoji で描くため、同じ絵文字でも絵柄が変わる。
   Twemoji を HTML 側でも使うには 1.4 MB のフォントを別途読ませることになり、
   待ち時間を減らしたいこの Issue と逆を向く

## 受信量の取り方

`WebAssembly.instantiateStreaming` は受信バイト数を教えてくれない。
`fetch` した `Response` の `body` を自前で読んで数え、同じ内容を新しい `Response` として
`instantiateStreaming` へ渡している（streaming のまま渡すので起動は遅くならない）。

判断が要った点。

- **数えられるのは解凍後のバイト数。** 圧縮配信では転送量と一致せず、
  3.8 MB の転送に対して表示は 21.4 MB まで増える。進捗の目安としては機能するのでこのまま出す。
  正確な転送量は起動後に Resource Timing から取り、画面右下へ出す
- **パーセント表示はしない。** 総量が要るが、圧縮配信では `Content-Length` が圧縮後の値になり、
  解凍後の総量が分からない。ビルド時に総量を埋め込む仕組みが要る。
  待ち時間そのものは変わらないので、必要になった時点で入れる
- **`Response` を作り直すと `Content-Type` の誤りをブラウザが検出しなくなる**ため、
  `application/wasm` かどうかを自分で確かめている。配信設定のミスはこのメッセージで分かる

## 失敗したときの扱い

| 決めたこと | 理由 |
| --- | --- |
| 失敗理由を画面へ出す | 実機では console を見られないことがある。YTA-10 からの方針を維持している |
| 再読み込みボタンを出す | iframe 埋め込みではブラウザの再読み込みが埋め込みページ全体に及ぶ。枠の中だけやり直せるようにする |
| 自動リトライはしない | 失敗の理由が分からないまま繰り返すと、転送量だけ増える。判断は利用者に委ねる |
| 遅いだけの回線を打ち切らない | タイムアウトで中断すると、あと少しで終わる読み込みを捨てることになる。10 秒を超えたら注意書きを足すだけにする |

## 実測値

Chrome の network throttling で、**事前圧縮した 3,988,231 bytes（brotli）** を実際に
ダウンロードさせて計測した。コミット `bd9ba53` + 本 Issue の変更、`dist/` をローカル配信。

| 条件 | キャッシュ | boot | うち download | 転送量 |
| --- | --- | --- | --- | --- |
| Fast 4G | なし | **4.14s** | 4.12s | 3.8MB |
| Slow 4G | なし | **22.79s** | 22.75s | 3.8MB |
| Slow 3G | なし | **81.85s** | 81.81s | 3.8MB |
| Slow 4G | あり | **0.10s** | 0.06s | 0（キャッシュから） |
| Fast 4G / iframe 1 つ | なし | **4.15s** | 4.13s | 3.8MB |
| Fast 4G / iframe 2 つ同時 | なし | 8.24s / 8.10s | 8.08s | 3.8MB × 2 |

読み取れること。

- **iframe 埋め込みによる差は無い。** 単体 4.14s に対し iframe 1 つで 4.15s。
  `iframe.html` で 8 秒かかるのは、検証ページが枠を 2 つ並べて同時に読み込むため
- **2 回目以降はキャッシュが効けば一瞬**（0.10s）。回線を絞ったままでもこの値になる。
  ただし現在はファイル名が `main.wasm` 固定なので、キャッシュ方針は配信基盤とあわせて決める必要がある
  （[wasm-delivery.md](wasm-delivery.md) の「配信側に必要な設定」を参照）
- **待ち時間のほぼ全部がダウンロード**で、instantiate は 0.05 秒未満
- **Slow 3G では 80 秒を超える。** 10 秒で出す注意書きが意味を持つのはこの領域。
  ここまで遅い回線を待てるようにするには、転送量をさらに削るか（フォントのサブセット化）、
  分割読み込みが要る。どちらも現時点では行わない

### この計測の限界

- **実機のモバイル回線では計測していない。** localhost に対する throttling なので、
  DNS・TLS・基地局側の遅延や、電波状況による速度変動は含まれない。**楽観側に出る**
- 実機で測るには公開 HTTPS のエンドポイントが要る。配信基盤の選定は Out of scope のため、
  この Issue では代用計測にとどめた

## 自動テストで確認できないこと

ロード中の表示はゲーム本体が動く前の HTML / JS 側にあり、`go test` の対象外。
上記の実測はすべて Chrome 上での手動確認で、次の挙動を確認している。

- 通常のロード（受信量が増え、起動後に消える）
- 10 秒を超えたときの注意書き
- `main.wasm` が 404 のとき（`Error: main.wasm: HTTP 404`）
- `Content-Type` が `application/wasm` でないとき
  （`Error: main.wasm: Content-Type is text/plain, expected application/wasm`）
- 再読み込みボタンで復帰できること
