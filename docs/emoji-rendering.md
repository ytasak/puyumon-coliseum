# カラー Emoji 描画の検証記録（YTA-7）

Emoji をキャラクター素材として使えるかを検証した結果と、採用した方式の根拠を残す。
ゲーム仕様そのものは Linear を参照すること。この文書は実装判断の記録に限る。

対象バージョン: Ebitengine v2.10.2 / Go 1.25.4

## 結論

Twemoji Mozilla 0.7.0（COLRv0）を同梱し、Ebitengine の `text/v2` で
Emoji 1 文字を固定サイズのセル画像へラスタライズして再利用する方式を採用した。
必須 12 グリフはすべてカラーグリフとして解決できている。

最大のコストは**フォント同梱そのものではなく `text/v2` のコード**で、
WebAssembly バイナリが 13.8 MB から 21.2 MB（gzip 3.35 MB → 5.30 MB）へ増えた。

## Ebitengine がサポートするカラーグリフ形式

`text/v2` のソース（`gotextfacesource.go` / `gotext.go`）で確認した。

| 形式 | 対応 | 備考 |
| --- | --- | --- |
| sbix / CBDT・EBDT（ビットマップ） | ○ | PNG / JPG / TIFF のビットマップをカラーとして扱う |
| COLRv0（レイヤーリスト） | ○ | ベクターのレイヤーを合成して描画する |
| SVG-in-OT | ○ | 内蔵の SVG ラスタライザで描画する |
| **COLRv1（ペイントグラフ）** | **×** | グラデーション・変形・合成は非対応。SVG テーブル → ベースグリフのアウトラインへフォールバックする |

## フォント候補の比較

必須 12 グリフ `🌴 🥺 😫 🤪 🐂 ⭐ ⚡ 🐋 💋 ❄️ 💥 💤` を実際にシェーピングし、
Ebitengine がカラーグリフとして扱うか（`text.Glyph.Colored`）を確認した結果。

| フォント | カラー形式 | ファイルサイズ | 結果 |
| --- | --- | --- | --- |
| **Twemoji Mozilla 0.7.0** | COLRv0 + CPAL（ベクター） | 1,474,284 bytes | **12/12 がカラー**。各 1 グリフ、送り幅は正方 1em |
| NotoColorEmoji | CBDT/CBLC ビットマップ（136px ストライク） | 10,673,480 bytes | 12/12 がカラー。ただしビットマップで拡大に弱く、送り幅が非正方（1.245em × 1.171em） |
| Noto-COLRv1 | COLRv1 | 4,991,984 bytes | **全滅**。`Colored=false` かつグリフ画像が nil で、何も描画されない |

Noto-COLRv1 が描画できないのは Ebitengine が COLRv1 のペイントグラフに対応しておらず、
このフォントには SVG テーブルも実体のあるアウトラインも無いため。

Twemoji を採用した理由は次の 3 点。

1. 必須グリフがすべてカラーで解決でき、ファイルサイズが候補中もっとも小さい
2. ベクターなので拡大縮小に強く、Composite Sprite（YTA-8）で部品ごとに倍率を変える用途に向く
3. 送り幅が正方 1em なので、Emoji ごとの位置補正なしに共通の描画単位を定義できる

`❄️`（U+2744 U+FE0F）のような異体字セレクタ付きの Emoji も 1 グリフへ解決された。

## 描画方式

Emoji は UI テキストではなくスプライト素材として扱うため、文字列を毎フレーム組版しない。
`internal/emoji` が Emoji 1 文字を **128px 四方のセル画像**へ 1 度だけラスタライズし、
以降は同じ `*ebiten.Image` を使い回す。表示サイズはセル画像の拡大縮小だけで決める。

- `text.Draw` 内部のグリフキャッシュは LRU で追い出されうるが、こちらで保持するセル画像は
  追い出されないため、毎フレームのフォント／グリフ初期化は発生しない
- セル生成は Ebitengine の描画コンテキストを必要とするため、`Image` の初回呼び出しまで遅延する。
  フォントの解析（`text.NewGoTextFaceSource`）は起動時に 1 度だけ行う

### glyph bounds / baseline / scaling

- **アンカーはグリフのインクではなく em box の中心に統一する。** `text.Draw` の
  `PrimaryAlign` / `SecondaryAlign` を `AlignCenter` にして、em box の中心をセル中心へ合わせる。
  ベースライン基準にすると Emoji ごとに上下位置がばらつくため使わない
- **セルは em box より大きく取る。** グリフのインクは em box をはみ出すことがあり、
  必須グリフでは `🤪` が最大で約 4%（サイズ 128px のとき 138×136px、オフセット (-5, -4)）。
  セル 128px に対して em box を 112px（0.875）とし、残りの余白ではみ出しを吸収する
- **拡大縮小は `FilterLinear`。** セルを一度ラスタライズしてから GPU 側で拡大縮小するため、
  サイズごとにグリフを作り直さない

## バンドルサイズへの影響

`GOOS=js GOARCH=wasm` でビルドした `main.wasm` の実測値。

| 状態 | main.wasm | gzip |
| --- | --- | --- |
| YTA-6 時点（`text/v2` 未使用） | 14,489,179 | 3,514,502 |
| `text/v2` を使用・フォント抜き | 20,712,048 | 4,829,181 |
| 現状（フォント同梱） | 22,185,948 | 5,561,948 |

増分の内訳は **コード +6.2 MB（gzip +1.3 MB）／フォント +1.4 MB（gzip +0.7 MB）**。
`text/v2` が `go-text/typesetting`・`golang.org/x/image`・`golang.org/x/text`・`srwiley/rasterx` を
引き込むため、フォント本体より**コードの増分の方が 4 倍以上大きい**。

削減の選択肢（いずれも本 PoC では未採用）:

- `-ldflags="-s -w"`: 21,656,630 bytes（gzip 5,459,415）。約 0.5 MB 減にとどまり効果は小さい
- フォントのサブセット化: 必要なグリフだけに絞れば数十 KB まで落ちるが、`fonttools` をビルド依存に
  追加することになる。使う Emoji が確定する段階で再検討する
- コード側の削減はフォントのサブセット化より効果が大きいが、`text/v2` を使う限り避けられない

## ライセンスと再配布

同梱フォントは `internal/emoji/assets/` に配置し、出典・SHA-256・ライセンス全文を同ディレクトリに置いた。

| 対象 | ライセンス | 再配布 |
| --- | --- | --- |
| フォント生成ツール類 | Apache License 2.0（Copyright 2016-2018, Mozilla Foundation） | 可 |
| 絵文字のデザイン（Twemoji） | CC-BY-4.0（Twitter, Inc. and other contributors） | 可。**クレジット表示が必要** |

CC-BY-4.0 はクレジット表示・ライセンスへのリンク・変更の有無の明示を求める。
配布物の `name` テーブルに copyright / license の項目が入っていないため、
リポジトリ側（`internal/emoji/assets/README.md` と `LICENSE.md`、および README のクレジット）で明示している。
**ゲームを配布する際は、クレジット表示をビルド成果物側にも残すこと。**

## 検証方法

- 必須グリフがカラーグリフへ解決されることは `go test ./internal/game/` で自動検証している
  （`TestPoCEmojiResolveToSingleColorGlyphs`）
- ヘッドレス環境では graphics context が無く pixel を読み出せないため、
  **色そのものは自動テストで検証できない**。実際の見た目は Desktop 起動とブラウザでの目視確認で担保する
